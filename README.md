# sqlite.v

[SQLite](https://sqlite.org) 3.53.4 translated from C to V with
[c2v](https://github.com/vlang/c2v).

The V sources mirror SQLite's source files: `btree.v` is `src/btree.c`,
`vdbe.v` is `src/vdbe.c`, `sqliteInt_h.v` is `src/sqliteInt.h`, and so on. They
are the translation of the SQLite amalgamation (`sqlite3.c`, 269,649 lines of
C, default compile options) into 87 files and 96,930 lines of V, without
comments. No part of it was edited by hand. It passes `v -check`, builds with
V 0.5.2, and passes SQLite's own test suite with the same results as the native
C build (see [Tests](#tests)).

## Files

- `name.v`: SQLite's `name.c`. Only sources with code in this build are
  translated (for example `os_win.c` is compiled out on macOS).
- `name_h.v`: the declarations of `name.h` (types, constants, ...).
- `parse_y.v`: the parts of the generated parser `parse.c` that Lemon copies
  from the grammar `parse.y`.
- `stmt.v`: only `sqlite3_sourceid()`, which the amalgamation appends after
  `stmt.c` (whose code is compiled out in this build).
- `0_globals.v`: the initialized global variables. V infers their types when it
  checks their declarations, file by file in name order, so they come first.
- `sqlite3.v`: the declarations of the C library functions the code uses, and
  helper functions of c2v.
- `example.v`: an example program.

## Usage

The files are translated C in `module main`: put them next to the files of your
program. The API is SQLite's C API with V names: `sqlite3_open()`,
`sqlite3_prepare_v2()`, `sqlite3_step()`, `sqlite3_column_text()`, ... and the
types `Sqlite3` and `Sqlite3_stmt`. [`example.v`](example.v) shows prepared
statements and `sqlite3_exec()` callbacks:

```
$ v -old-compiler -w run .
SQLite 3.53.4
inserted 3 rows, last rowid 3
1: alice 9.5
3: carol 8.0
n=3 avg=8.25 names=alice, bob, carol
sum=55 approx=3.143
```

Notes:

- Build with `-old-compiler`: V's new backend computes one `offsetof`
  expression in SQLite incorrectly. `-w` hides V's warnings about the
  translated C code. Add `-prod` for an optimized build.
- C code is translated for one target: the declarations and constants of the
  system headers (struct layouts, `F_SETLK`, ...) are those of the machine that
  ran c2v. These files were generated on macOS 26 (arm64, Apple Clang 21). For
  another platform, regenerate them there (below).

## Tests

SQLite's test suite is a set of Tcl scripts run by `testfixture`: a Tcl
interpreter with SQLite and SQLite's C test code built in. To run it against
translated code, [`testfixture/run.sh`](testfixture/run.sh) translates the
whole test harness with c2v into one V program: `sqlite3.c` (built with the
test options `make testfixture` uses), the Tcl interface, and 84 C files of
test code and extensions (86 files, 542,073 lines of C, unmodified). It then
builds it with V and runs SQLite's `test/testrunner.tcl` with it.

Results on macOS 26 (arm64), Tcl 8.6.18, V 0.5.2 (b98993c):

| suite       | V (translated, unoptimized build)     | native C build (`-O2`)                |
|-------------|---------------------------------------|---------------------------------------|
| `veryquick` | 1 error out of 329,786 tests, 1:10    | 1 error out of 329,782 tests, 1:10    |
| `full`      | 3 errors out of 1,033,896 tests, 6:30 | 3 errors out of 1,033,933 tests, 7:22 |

(18 parallel test processes. The test counts differ slightly between runs:
some tests are randomized or timing dependent.)

The failures are the same in both builds:

- `loadext.test` (2 tests): the expected `dlopen()` error message does not
  match the wording of macOS.
- `vtabH.test`: walks the whole file system and does not finish in reasonable
  time; the script stops it after a minute.

The script also lowers the limit of open files to 1024: `misc7.test` opens
files until the limit is reached, which takes hours with the unlimited default
of macOS (for the native build too).

To reproduce (needs c2v 13f6a18 or newer):

```sh
brew install tcl-tk@8
curl -O https://www.sqlite.org/2026/sqlite-src-3530400.zip && unzip sqlite-src-3530400.zip
git clone https://github.com/vlang/c2v && (cd c2v && v -o c2v .)
SQLITE_SRC=sqlite-src-3530400 C2V=$PWD/c2v/c2v testfixture/run.sh full
```

The script also builds SQLite natively: that generates some of the compiled
files and gives a native `testfixture` to compare with. c2v, built with V
0.5.2 (b98993c), needs about 17 GB of memory for `sqlite3.c`, whose Clang AST
is 740 MB of JSON.

## Regenerating the V files

They were generated by c2v 13f6a18 from the amalgamation that SQLite's build
generates with `#line` directives, which name the original source files:

```sh
curl -O https://www.sqlite.org/2026/sqlite-src-3530400.zip && unzip sqlite-src-3530400.zip
mkdir build && cd build
../sqlite-src-3530400/configure --linemacros && make sqlite3.c
GC_INITIAL_HEAP_SIZE=16000000000 c2v -split_files -skip_comments sqlite3.c
```

c2v writes the files to `build/c2v_output/`. `-split_files` writes one V file
per original source file, `-skip_comments` leaves out all comments. Apart from
its 843 `#line` lines, this `sqlite3.c` is identical to the one in
[sqlite-amalgamation-3530400.zip](https://www.sqlite.org/2026/sqlite-amalgamation-3530400.zip)
(SHA-256 `1e71ddf93849c6a6ecf58b827c0692073d2dd7ee40196158068f7b29f422e87d`).
The directives change one thing in the translation: `__LINE__`, which SQLite
passes to its error logging (`sqlite3_corrupt_error(2293)`), is the line in the
original source file.

Translating takes about 20 seconds; the large initial GC heap makes c2v several
times faster on the 740 MB AST. c2v formats its output with `v fmt`, so the same
`v` must be in `PATH` to get identical files.
